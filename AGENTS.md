> ## ⛔ CRITICAL — Git & version control (overrides every other instruction)
>
> - **NEVER run `git push`. Ever. Under any circumstances.** The user pushes and deploys themselves.
> - **NEVER run `git commit` or `git add`** unless the user explicitly requests that exact action in their current message. A "yes" from an earlier turn does **not** carry forward — approval is per-action and does not persist.
> - **Only make code modifications that have been explicitly discussed and approved** in the conversation. Do not bundle in unrelated edits.
> - When work is ready, **stop and report** — let the user stage, commit, and push. If you believe a commit/push is warranted, *ask*; do not act.

This file gives guidance to AI coding agents (Claude Code, Codex, Cursor, Copilot, …) and to human developers working in this repository.

## Working rules (all agents, all developers)

### 1. Agent instruction files — `AGENTS.md` is the source of truth
- Project knowledge for coding agents lives ONLY in `AGENTS.md` files: root `AGENTS.md` (this file), `src/app/AGENTS.md`, `src/lib/AGENTS.md`.
- Every `CLAUDE.md` is a one-line stub containing `@AGENTS.md` (Claude Code expands that import). **Never write content into a `CLAUDE.md`** — edit the `AGENTS.md` next to it. No copies, so nothing can drift.
- New subsystem notes in a folder → create `<folder>/AGENTS.md` with the content AND `<folder>/CLAUDE.md` containing only `@AGENTS.md`. List the new file under "Subsystem details" below.
- When a change makes a note wrong, update the note in the same change set.

### 2. Documentation and specs
- Language: all system documentation, specs and code comments are in **English**. The product UI stays in **Russian**; quote Russian UI labels exactly, with an English gloss on first use, e.g. «Компании» (Companies).
- `docs/docs/` — general system description (overview, architecture, data model, modules, operations). Keep it current when a change affects it.
- `docs/specs/<topic>/` — specs, **one topic per sub-folder**, kebab-case name (e.g. `auth/`, `billing/`, `db-migrations/`). A topic folder holds ONLY specs for that topic: `auth/` is only for authentication changes. Unrelated work gets its own folder, even when it ships in the same change set.
- Each topic folder has a `README.md` (summary, status, index of files). `docs/specs/README.md` lists every topic folder — add a row when you create one.
- `docs/todo/README.md` — decided but NOT scheduled work (postponed items with their spec source). When an item is scheduled, move it into its spec folder and delete it there.

### 3. Database changes — Drizzle migrations only
- **Every** database structure change goes through a Drizzle migration file in `migrations/`, committed with the code that needs it. Baseline = `migrations/0000…0004` (2026-11-13; `0004` = platform reference/seed data); the production DB is tracked in `drizzle.__drizzle_migrations`.
- Schema change: edit `src/db/schema.ts` → `pnpm db:generate --name <what>` → review the SQL → commit both.
- Change that `schema.ts` cannot express (extensions, SQL functions, generated columns kept out of the schema, data backfills, renames needing care): `pnpm db:custom --name <what>` → write the SQL into the new empty file. Make it safe to re-run where you can (`IF NOT EXISTS`, guarded `DO` blocks).
- Apply: `pnpm db:migrate` (uses `DATABASE_URL`). Run it against each target DB **before** deploying code that needs the change. `pnpm db:check` validates the migration folder.
- **Never** use `drizzle-kit push`, never change the schema with ad-hoc SQL / one-off scripts / the Neon console, and never edit a migration that has already been applied — write a new one.
- Generated SQL may be edited before it is applied (add a comment explaining why). Data-only fixes (deleting test rows, cleanups) are not schema changes, but if they must be repeatable on other DBs, put them in a custom migration too.
- **Platform reference data** (rows every DB needs: source templates, system funnel stages) lives in migrations with fixed ids and `ON CONFLICT DO NOTHING`; change it with a NEW migration. Tenant data (orgs, users, companies, org-owned stages/rules, …) never goes into a migration.

**Subsystem details live in nested files:**
- `src/app/AGENTS.md` — feature flows: **global search** (`/api/search`, reachable from every page's header) and the **global AI chat panel** (also reachable from every page, mounted once at the layout level), **analytics (sales reporting over orders — `/analytics`)**, invitation flow, sources (Nylas/**IMAP**/Chat/Drive/Files Drop Off/**AI Chat** (chat segments + chat files as source items)/**Telegram bot** — per-org webhook push; email parser also folds **calendar (.ics) invites** into the parent item; **own-org attribution** of every parsed item; admin **source teardown/reset**), **companies** (`/clients` — 5 relationship tabs, scroll-loaded feed, + **batch web enrichment**, owner-managed **discovery blocklist**) and a **standalone contacts directory** (`/contacts`), tasks (Kanban + Timeline), **deals (sales funnel + topics deal bridge UI)**, **products (catalog) & orders (manual builder + guest order-confirmation links + LLM-assisted "order from request" assembly)**, **documents (attachments) of companies / contacts / deals / tasks / orders** (stored originals, automatic + manual links, upload, file route), **contact ↔ company links over time**, **Telegram files + groups**, **UI state the app remembers** (sidebar cookie, `usePersistentTab`), org member management.
- `src/lib/AGENTS.md` — logic/infra: email delivery (Nylas only), Google infrastructure, per-source credentials + their encryption, **AI chat** (route, tools, history, chat as a source, files + voice notes, draft cards, eval), the AI chat **records** and **statistics** engines, entity search normalisation, json-render catalog/registry.

### 4. Database access — ONLY in `src/server/` (lint-enforced)
- Only `src/server/**` may read or write the DB (plus `src/db/**` = the client + schema, and `src/lib/auth.ts` = the better-auth Drizzle adapter). API routes, pages, layouts, components, hooks, `src/lib`, workflows and `src/proxy.ts` call a server function instead — never `db`, never a query builder.
- Put the query in a `src/server` module that starts with `import "server-only"` (NOT `"use server"` when it takes an org / user id — see rule 5) and takes the ids as explicit params; the route keeps only session check, input validation and the HTTP response.
- `import type` from `@/db/schema` / `drizzle-orm` is fine anywhere. DB enum VALUE lists for validation come from `src/server/db-enums.ts`.
- ESLint (`DB_ACCESS` in `eslint.config.mjs`) fails the build on any value import of `@/db/*`, `drizzle-orm`, `@neondatabase/*` outside those folders. Do not disable it per line; move the code.

### 5. Access — nothing works without sign-in
- `src/proxy.ts` rejects every request without a session (API → 401, page → `/sign-in`), except the allowlist of public-by-design entry points documented in `docs/specs/auth/api-access.md`. Adding a public entry point = a documented reason + its own protection + a row in that spec + a pattern in `src/proxy.ts`.
- The gate is a safety net, not the check: every route handler and every exported function of a `"use server"` module must validate the session itself (`getServerSession()` + 401, or a `require*` helper).
- Internal helpers that take an org / user id as a parameter must not live in a `"use server"` module — use `import "server-only"`.

## Commands

- `pnpm dev` — start Next.js dev server. **Runs with `NODE_OPTIONS=--max-old-space-size=8192` on purpose** (same for `pnpm build`). `withWorkflow()` bundles the WHOLE app on boot to scan for `'use workflow'` / `'use step'` directives ("Discovering workflow directives …" in the dev log), so the dev server sits at **~4.1 GB RSS while completely idle** — right against Node's default ~4.19 GB heap ceiling. Loading one or two heavy pages pushes it over and the process **dies with no error message** — the log just stops, typically right after `Created intermediate workflow bundle`, which reads as "the dev server silently quit". Raising the ceiling is the fix; don't remove the flag. ### Auth Flow

- Server sessions: `src/lib/get-session.ts` uses `cache()` to dedupe session calls per request.
- Client auth: `src/lib/auth-client.ts` exports `authClient` with organization, admin, apiKey, emailOTP plugins. (Polar payments were removed — no billing in the app.)
- Auth config: `src/lib/auth.ts` — 7-day sessions with **`session.cookieCache` enabled (5-min signed cookie)** so navigation doesn't hit the DB every request — without it a transient Neon blip made `getSession()` return null → the `(protected)` layout bounced to `/sign-in`, reading as a random mid-session logout. `databaseHooks.user.create.after` skips default-org creation when the new user's email has a live (pending + non-expired) invitation — otherwise they'd end up in two orgs (default + inviter's).
- Sign-in methods: **email OTP only** — a 6-digit code (5 min expiry) sent to the email. Email/password, password reset, and Google/GitHub OAuth are removed (`emailAndPassword`, `socialProviders`, `oAuthProxy`, `lastLoginMethod` are gone from `auth.ts`). `emailOTP` runs with `disableSignUp: false`, so the code also **registers** a new user on first login. `/sign-in`, `/sign-up` and the accept-invitation page all use one two-step component, `src/components/forms/form-email-otp.tsx` (email [+ name] → `InputOTP` → `authClient.signIn.emailOtp({ email, otp, name })`; `name` is only used for a new user). `/sign-up` asks for the name; a new user who comes through `/sign-in` gets the email's local part as name (`databaseHooks.user.create.before`). OTP emails go through `sendEmails` in `src/lib/email.ts`.

### Role Model (Two-Tier)

- **Platform roles** (`user.role`, via admin plugin): `user` | `admin`. Controls access to Settings page + platform-wide admin functions.
- **Organization roles** (`member.role`, via organization plugin): `owner` | `admin` | `member`. Controls within-org permissions (member management, org editing, invitations).
- Independent: a platform `user` can be org `owner`.
- **Org data edit = owner only, server-side** (identity I1, spec §3.4): `organizationHooks.beforeUpdateOrganization` in `src/lib/auth.ts` refuses better-auth's `organization.update` for any non-owner (403 — better-auth's default access control also lets `admin`). The same hooks (`afterUpdateOrganization`, `afterAddMember`, `afterRemoveMember`, `afterAcceptInvitation`) and the platform-admin edits in `src/server/admin-organizations.ts` call `invalidateOwnOrgContext(orgId)`.

### Multi-Tenancy

Session stores active organization (id, name, slug). **The org `logo` is intentionally NOT on the session** — logos are base64 data URLs (often 100KB+) and `auth.ts`'s `cookieCache` serialises every session field into the signed session cookie, so a logo overflowed the ~16KB HTTP header limit → `431 Request Header Fields Too Large` on every authenticated request (dev + Vercel). The sidebar loads the logo server-side in `(protected)/layout.tsx` and passes it as the `orgLogo` prop instead (`user.image` data URLs are the same hazard — keep avatars/logos as hosted URLs, not data URLs). All feature tables (clients, contacts, tasks, **deals**, **products**, **orders**, **order_requests**, rules, **sources, source_items**, **discovery_blocklist**) are org-scoped via `session.session.activeOrganizationId`; no cross-org read/write. Permission checks live in the module servers (`requireOrgContext`, `requireOrgOwner`, `requireOwnerOrg`, `requireAdmin`, `getActiveOrgRole`). **Exception:** the admin source-teardown tool (`/api/admin/teardown/*`) is platform-admin-only and intentionally cross-org (it resolves one source's owning org and operates within it). **Exception:** the guest order-confirmation flow (`/o/[token]` + `order_access_link`) is intentionally org-unscoped — the opaque token *is* the authorization, and the resolver loads the order strictly by `grant.order_id`.

**Deal funnel stages scope model** (`deal_funnel_stage`):

### Daily Orchestration (sync → parse → upload pipeline)

Scheduled batch processing of the Sources subsystem. Three layers, deliberately split so the Vercel Workflow SDK can be ripped out and replaced (BullMQ / Trigger.dev / VPS cron) without touching business logic.

- **`src/server/orchestration/`** — engine-agnostic. `runDailyPipeline({ trigger })` is the single callable entry point: first refreshes the AI model registry (`syncAllModelCatalogs()`, phase 0 — isolated, errors logged as phase `catalog`; also AI chat segments → source items `ingestDueChatThreads(null)` and AI chat history retention `purgeChatThreads()` — 90 days), then runs `runFullSync()`, then loops `parseSourceItem()` over `listPendingParseIds()`, then loops `uploadSourceItem()` over `listPendingUploadIds()`. Sequential by design (MVP scale). Per-item failures are isolated three layers deep — `parseSourceItem`/`uploadSourceItem` already return-on-error, the loops wrap each call in their own try/catch, and `pipeline_run.errors_json` records every failure without crashing the run. Caps + cron schedule live in `src/server/orchestration/config.ts` (possible follow-up: lift these to a system_settings dictionary).
- **Per-source automation gate (`source.automated_parsing_is_allowed`)** — boolean column, default `true`. All three orchestration phases filter on it: `runFullSync()` skips sources with the flag off; `listPendingParseIds()` / `listPendingUploadIds()` (and their `count*Total` siblings) inner-join `source` and require the flag to be true, so any items already in the queue under a flagged-off source are also skipped. Manual UI actions (`/api/sources/{sync,items/[id]/parse,items/[id]/reparse,r2/save,dropoff/upload}`) bypass the flag — operator intent overrides the schedule. Org owners flip it from the Sources page "Manage organization sources" tab; platform admins flip it from `/settings`.
- **`src/server/upload-source-item.ts`** — `uploadSourceItem(itemId)` server function extracted from the manual R2 save route. Returns `{ ok, … }` instead of throwing. The manual `/api/sources/r2/save` route is now a thin auth wrapper that calls it; the orchestration layer calls the same function directly.
- **`pipeline_run` table** (`src/db/schema.ts`) — one row per orchestration run with per-phase counts (`syncSourcesSucceeded` / `parseComplete` / `uploadFailed` / etc.) and a bounded `errorsJson: { phase, sourceId?, sourceItemId?, message }[]`. Future Sources-page widget reads from here.
- **`src/workflows/daily-pipeline.workflow.ts`** (and its hourly sibling `src/workflows/topics-pipeline.workflow.ts`) — the **only** files that import the Vercel Workflow SDK (`'use workflow'` / `'use step'` directives, `next.config.ts`'s `withWorkflow()` wrapper; package `workflow` ≥ 4.8 — 4.2 broke `next build` with AI SDK 7, whose packages carry Workflow serialization markers that pulled `@vercel/oidc` into the step bundle). Single coarse step that calls `runDailyPipeline({ trigger: 'cron' })`. Replacing this file + the cron route is the entire delete list when migrating off Vercel Workflows. Trade-off: workflow-level retry of the single step would create a second `pipeline_run` row — acceptable since per-item errors are already swallowed; if it becomes an issue, add a stale-run sweep keyed on `status='running' AND started_at < now() - 1h`.
- **`src/app/api/cron/daily/route.ts`** — Vercel Cron Jobs entrypoint. Validates `Authorization: Bearer $CRON_SECRET` in every environment (Vercel auto-attaches this header on scheduled invocations; an unset `CRON_SECRET` rejects all calls). Calls `start(dailyPipelineWorkflow, [])` from `workflow/api`.
- **`vercel.ts`** — declares `crons: [{ path: "/api/cron/daily", schedule: ORCHESTRATION_CONFIG.cron }]` (replaces the older `vercel.json`). Imports the constants file so cadence is one-edit-in-one-place.
- **`src/app/api/admin/pipeline/run/route.ts`** — admin-gated POST that invokes `runDailyPipeline({ trigger: 'manual' })` synchronously. Lets you exercise the full chain without waiting for cron. `maxDuration = 300` (the Vercel default ceiling) because phase 2 can chew through `maxParsePerRun` items (some of which are videos) — for production-scale runs, prefer the workflow path.
- **Auto-generated routes** at `src/app/.well-known/workflow/v1/{flow,step,webhook}/` are produced by `next build` from the workflow source — gitignored + eslint-ignored. Source of truth is `src/workflows/*.workflow.ts`.

### Object storage (`src/server/storage/`) — every stored file goes through here

Spec: `docs/specs/s3-r2/`. Generic S3-compatible core + provider registry; Cloudflare R2 is today's only provider.

- **Rule for business code** (lint-enforced): store/read objects only via `@/server/storage` — `putObject(key, bytes, contentType)`, `putTextObject(key, text, contentType)`, `getObject(key)` (→ `{ bytes, contentType } | null`), `getTextObject(key)` (throws `StorageObjectNotFoundError`), `deleteObjects(keys)` (chunked, idempotent), `checkStorage()`, `storageInfo()`. Never import `@aws-sdk/*` or read `process.env.R2_*` / `STORAGE_*` outside the layer.
- `s3/client.ts` — the generic core, the ONLY `@aws-sdk/*` importer (portable S3 subset: Put/Get/DeleteObjects/HeadBucket; not-found detection).
- `providers/<key>.ts` — vendor specifics (env var names, endpoint rules, region, quirks via `clientOptions`); `providers/index.ts` = registry, active provider from `STORAGE_PROVIDER` (default `cloudflare-r2`). Adding a provider = one file + one registry line + env + copy the objects; no business code change.
- Storage config is env-only on purpose (no DB table): a provider switch is a data migration, not a runtime choice.
- **Key layout**: parsed markdown `org_<orgId>/source_<sourceId>/item_<itemId>.md` (`source_item.markdown_r2_key`); **original document files** `org_<orgId>/files/<itemId>/<safe name>` (`source_item.file_key`, documents spec `docs/specs/attachments/` §3.2, ≤ 50 MB, written by `storeDocumentFile` in `src/server/documents.ts`); avatars `avatars/user_<id>`. Teardown deletes both keys of every deleted item; a reparse deletes its children's objects (`carryDocumentLinksForReparse`); «Удалить файл» deletes an upload's objects.
- **Legacy names** (kept until a second provider, Phase 2 of the spec): DB `source_item.markdown_r2_key` / `r2_upload_status` / `r2_uploaded_at` / `markdown_r2_size_bytes`, routes `/api/sources/r2/*`, `r2-batch-upload-control.tsx`, `teardown_log.counts.r2Objects` — they mean "object storage". UI text says «хранилище», never the vendor.
- ⚠ `eslint.config.mjs` builds ALL layer-boundary rules (AI + storage + DB access) from shared parts per folder scope, with `@typescript-eslint/no-restricted-imports` (core `no-restricted-imports` off; `allowTypeImports` for the DB rule): a later flat-config block that sets the same rule REPLACES the earlier one, so never add a separate `@typescript-eslint/no-restricted-imports` / `no-restricted-syntax` block for `src/**`.

## Environment Variables

Required in `.env`: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_APP_URL` (base URL for invitation email links; also read by the client-side `authClient` in `src/lib/auth-client.ts`), `AI_GATEWAY_API_KEY` (Vercel AI Gateway key — single auth for all LLM calls; replaces the previous per-provider OpenAI / Vertex credentials), `NYLAS_API_KEY`, `NYLAS_API_URI`, `NYLAS_CLIENT_ID`, `NYLAS_CALLBACK_URI` (the **platform** Nylas application — authenticates Truffalo's own Nylas account. Used by `sendEmails` and as the **fallback** connection for email sources. An org that connected its mailbox in its OWN Nylas account overrides `NYLAS_API_KEY` / `NYLAS_API_URI` per-source via `credentials_ref.apiKey` / `.apiUri` — see `src/lib/AGENTS.md` § "Per-source credentials"), `CREDENTIALS_ENCRYPTION_KEY` (base64-encoded 32 random bytes — generate with `openssl rand -base64 32`. AES-256-GCM key for encrypting `source.credentials_ref` blobs via `src/lib/credentials-crypto.ts`. **Losing this key permanently bricks every encrypted source credential in the DB** — store as a Vercel encrypted env var, never commit, never rotate without a re-encrypt migration. Wire format now carries a 1-byte version prefix (v1 = `0x01`) so future rotation can land without re-encrypting in a flag day — see `src/lib/AGENTS.md` § "Credentials encryption"), `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, `R2_PUBLIC_URL` (Cloudflare R2 — S3-compatible object storage for parsed-source markdown. `R2_PUBLIC_URL` is the S3 endpoint, e.g. `https://<account>.eu.r2.cloudflarestorage.com` for EU jurisdictional buckets; the R2 provider falls back to `R2_ENDPOINT`-less construction `https://<R2_ACCOUNT_ID>[.<R2_JURISDICTION>].r2.cloudflarestorage.com` if it's unset; these vars are read ONLY by `src/server/storage/providers/cloudflare-r2.ts`. Optional: `STORAGE_PROVIDER` (default `cloudflare-r2`), `R2_ENDPOINT` (preferred name for the endpoint), `R2_JURISDICTION` (`eu` / `fedramp`)), `CRON_SECRET` (base64-encoded 32 random bytes — generate with `openssl rand -base64 32`. Auth token for `/api/cron/daily`; Vercel Cron Jobs auto-attach `Authorization: Bearer $CRON_SECRET` to every scheduled invocation when this var is set as a project env var. Checked in every environment; unset = every call rejected. Set the same value in `.env` and on Vercel Production. Rotate by generating a new value, updating both places, and the next scheduled run uses the new one).

**Source-credentials env vars (Phase 3 — bootstrap-only):** `NYLAS_GRANT_ID`, `GOOGLE_CHAT_CREDENTIALS` (base64-encoded service account JSON), `GOOGLE_CHAT_IMPERSONATE_USER`, `GOOGLE_CHAT_PROJECT_NUMBER`. After Phase 3 these are read **only** by `scripts/migrate-credentials-to-db.ts` to seed existing rows' `credentials_ref` on first run. Runtime reads come from `credentials_ref` only:
- **nylas** keeps a fallback to `NYLAS_GRANT_ID` (logs a warning when used) so unmigrated rows still bootstrap. The per-source `apiKey` / `apiUri` are likewise optional and fall back to `NYLAS_API_KEY` / `NYLAS_API_URI` — a source only needs them when the org uses its own Nylas application.
- **gchat / gdrive** have NO fallback — runtime throws `MissingCredentialsError` if `credentials_ref` is null on a row.

Once every row has `credentials_ref` populated in production, these env vars become vestigial. Org owners replace them with their own per-org credentials via Sources → "Manage organization sources" → Configure.

**Telegram bootstrap env vars (optional):** `TELEGRAM_BOT_TOKEN` + `TELEGRAM_WEBHOOK_SECRET_TOKEN`. Telegram bot credentials are **per-org** (`credentials_ref = { botToken, webhookSecret }`, configured via Sources → Configure). These two env vars are a **nylas-style fallback**: `getTelegramCredentials` reads them (logs a warning) only when a telegram source's `credentials_ref` is null — a single bootstrap bot before the UI is used. `webhookSecret` is a high-entropy string YOU generate (Telegram echoes it in `X-Telegram-Bot-Api-Secret-Token` for forgery rejection). **`NEXT_PUBLIC_APP_URL` must be the public HTTPS origin on Vercel** or webhook auto-registration on credential-save is skipped (then the webhook must be registered manually — error-prone). `TELEGRAM_BOT_USERNAME` is unused at runtime today (botUsername lives in `provider_config`); reserved for Phase 3 group @-mention detection.

Email delivery: system mail goes through Nylas only (`NYLAS_API_KEY`, `NYLAS_API_URI`, `NYLAS_GRANT_ID` with a send scope). `EMAIL_PROVIDER`, `RESEND_API_KEY` and `RESEND_FROM` are no longer read (Resend removed 2026-11-16).

**In production (Vercel)**: `BETTER_AUTH_URL` and `NEXT_PUBLIC_APP_URL` must be the real deployed origin (e.g. `https://app.truffalo.ai`). `NEXT_PUBLIC_*` is baked into the client bundle at build — changes require a fresh deploy. The `.env.vercel` file in the repo root is **reference-only**, not auto-synced to Vercel.
