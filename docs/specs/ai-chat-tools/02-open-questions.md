# 02 — Questions and decisions

All decided 2026-11-16 by the product owner: every question **as recommended**, except Q10 and Q15 (see «Decision»). New questions found during the build are added as Q23+.

| # | Question | Options | Rec. | Decision |
|---|---|---|---|---|
| Q1 | **How is a write confirmed?** | A — draft card in the chat, the user can edit values and clicks «Создать» (the write is a normal UI request, not a model tool). B — AI SDK tool approval: the user approves the model's tool call as it is (no editing). C — create at once, with «Отменить» for 24 h | **A** (only A lets the user fix a misread phone, see duplicates first and confirm a company + contact together) | as recommended |
| Q2 | **Scope of the first release** | A — the 3 requested actions: company / contact, deal, task (+ attach the input file as a document). B — A + «Дополнить существующую запись» + links (contact ↔ company, contact → deal) + «Записать встречу». C — B + order request, deal stage move, task done / due change | **B** (A first in the plan; the B items are what users ask for right after a card scan: «this person is already there — add the new phone») | as recommended |
| Q3 | **May the chat change EXISTING records?** | A — no, only create. B — only fill EMPTY fields and add aliases / extra addresses (never overwrite). C — also overwrite, with an old → new diff in the card | **B** for the first release; C later | as recommended |
| Q4 | **Recorded voice messages** | A — yes: a record button, WAV in the browser, parsed by the audio parser (transcript + speakers). B — only browser dictation (exists) | **A** (dictation loses names / numbers and has no speakers; a recorded message is also kept as a document) | as recommended |
| Q5 | **Files accepted in the chat** | A — like «Files Drop Off»: images, PDF, DOCX, PPTX, audio, video (≤ 50 MB), text. B — A without video | **A**, through direct upload to storage (§5.1) — needed anyway, since a Vercel function takes ≤ 4.5 MB per request | as recommended |
| Q6 | **Signals during the turn** (`readSignals`: extractor + funnel rules → suggested actions) | A — yes, when the user reports business facts (≈ $0.002 per such turn). B — no; the chat model alone decides; signals only via the CH6 ingest later | **A** (the funnel rules of the org — which stage, which type — then drive the deal draft, not the model's guess) | as recommended |
| Q7 | **Exact duplicate** (same e-mail / phone / domain as an existing record) | A — «Использовать существующий» is the default, «Всё равно создать» needs an extra click. B — refuse to create | **A** | as recommended |
| Q8 | **Required fields / what to ask** | Task due date: ask (A) or default «tomorrow 18:00» (B). Contact without company AND without any channel: ask (A) or allow (B). Deal stage: first `active` stage (A) or ask (B) | Task due: **A** (ask) · contact: **A** (ask) · deal stage: **A** (first active stage, editable; the funnel rule suggestion of Q6 shown) | as recommended |
| Q9 | **Clarification style** | A — question + quick-reply buttons (`askUser`), max 2 per turn. B — questions in prose only | **A** | as recommended |
| Q10 | **Undo after create** | A — «Отменить» for 24 h while the record is unchanged (soft delete, `status = deleted`). B — none (the user deletes in the CRM) | **A** | **Skipped for now** — no undo; a wrong record is changed / deleted in the CRM as usual |
| Q11 | **Deals created by a person in the chat and the go / no-go entry gate** (`deals.entryGate`) | A — like a deal made in the UI: no gate. B — gated like the automatic bridge | **A** | as recommended |
| Q12 | **Page context** (the user is on a company page and says «добавь контакт Иван Петров, +7…») | A — the page company is the default company of the draft. B — always ask | **A** (default, shown in the card) | as recommended |
| Q13 | **Bulk** (a list of 30 companies pasted / a photo of 10 cards) | A — ≤ 10 drafts per turn, «Создать всё»; more → «это импорт, используйте …». B — no limit | **A** (bulk import is a separate feature) | as recommended |
| Q14 | **Who may confirm** | A — any org member (as in the UI). B — only owners / admins of the org | **A** | as recommended |
| Q15 | **Provenance on the record** («Создано из ИИ чата») | A — a line in the record's activity / description + the input file as a document. B — a new column `created_via = ai_chat` on company / contact / deal / task (migration) shown as a badge. C — nothing | **B** (filterable, e.g. «what did the chat create this week»), plus the document | **No new column, no badge**: creator = the record's `user_id` (+ the deal's `deal_activity` row); source = the `ai_chat_action` row (thread, message, files, created ids) + the input file as a document (Q16) + `deal_activity.source_item_id` for a deal |
| Q16 | **Business card file → document of the contact** | A — on by default («Прикрепить файл» checked). B — off by default | **A** | as recommended |
| Q17 | **Web enrichment of a new company** | A — follow the org setting `clients.enrichOnCreate` (as the UI). B — always offer «Заполнить из интернета» in the card | **A**, plus the card button when the setting is off | as recommended |
| Q18 | **Chat notes and the CH6 ingest after a confirmed action** | A — ingest as today; the confirmed actions ride on the segment item so the deal bridge links instead of duplicating, and topic cards do not re-suggest a created task. B — skip signal extraction for segments that already produced actions | **A** (the note still carries other facts) | as recommended |
| Q19 | **Rate limits** | ≤ 10 drafts per turn, ≤ 30 creates per user per hour | as proposed | as recommended |
| Q20 | **Eval fixtures** | Synthetic business cards (generated PNG), synthetic TTS voice, written meeting notes — kept in the repo (no real people's data) | yes | as recommended |
| Q21 | **Model for card / voice reading** | A — the existing parsers (image / audio) + the chat model. B — a dedicated structured extraction process «Карточка контакта» (`chat.entity_extraction`) on top of the parsed text, eval-tuned | **A** first; **B** only if the eval shows missed fields (the image parser puts a card's own person into «senders») | as recommended |
| Q22 | **Attachments and the chat model** (owner, 2026-11-16) | Detach every attachment from the chat and process it like a mail attachment (source item + original + the parser of its type); the chat model gets ONLY the text; no file (also no image) is sent to the chat model, in any turn | — | **Decided as stated** (01 §5.2); consequence: `chat.assistant` no longer requires `image_input` |
| Q23 | **Blurred photos: the image parser invents text** (found in T1, 2026-11-16) | On a heavily blurred business card Gemini 2.5 Flash (`parsing.image`) wrote a made-up phone and e-mail in 1 of 3 runs, even with the new rule «write [неразборчиво], never guess». Such a value is IN the parsed text, so the draft grounding (§8.2) cannot catch it. Built now: the parser rule (2 of 3 runs mark the text) + the draft does not prefill phone / e-mail / site / Telegram from a file with the marker + filler numbers («+7 999 999 99 99») removed. Options for the rest: A — accept (the card shows «из файла «…»» next to each value; the user sees the photo). B — a sharpness check of the image before parsing (`sharp`, Laplacian variance; a blurred photo → no channels prefilled + «Фото нечёткое, переснимите»). C — a second model pass «is this value legible?» per contact value (+1 call per card). D — the dedicated extraction process of Q21-B with a stricter model | **A now, B if users report it** (B is deterministic and cheap; C / D cost a call and still trust a model) | **A** (2026-11-16); B only if users report it |
